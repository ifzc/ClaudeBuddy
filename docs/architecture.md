# 实现原理

## 进程内覆盖

工具通过 Frida 启动目标应用，在主进程恢复执行前加载 `agent.js`。脚本覆盖 Windows 时区查询与本地时间转换接口；UTC 时钟和时间戳保持原样。

覆盖包括 `GetTimeZoneInformation`、`GetDynamicTimeZoneInformation`、`GetLocalTime`、隐式使用系统时区的 SYSTEMTIME / FILETIME 转换，以及可用 ICU 模块中的默认时区入口。转换使用 Windows 返回的时区规则，避免把纽约等地区简化为全年固定偏移。

## 应用隔离

飞书主进程启用 child gating，对它拥有的 `Feishu.exe --type=renderer` 子进程应用相同覆盖，随后恢复执行。辅助进程直接恢复。微信 4.x 的聊天界面位于主进程，因此只处理该主进程，不启用子进程覆盖。

每个应用有独立控制器与配置。共享 Frida device 时，回调只处理自身 session 所属的子进程，避免提前恢复另一个控制器正在处理的子进程。

## 生命周期

关闭设置窗口时，有活动会话或启动/恢复任务就收起到系统托盘，后台事件循环与 Frida 会话继续运行。因此已有进程的时区不会被撤销，飞书后续创建的 renderer 也继续接受相同覆盖。点击托盘图标重新打开设置；只有用户主动点击“恢复普通启动”才会重启对应应用。没有活动会话或任务时，关闭窗口直接退出工具。

GUI 在后台线程执行启动和恢复，通过队列更新界面。恢复操作需用户确认，使用已持有的原始进程句柄判断它是否仍存活，避免 PID 被复用时误终止其他程序。然后退出该应用的进程树、释放 Frida session，并普通启动应用。顺序很重要：在多线程应用仍运行时卸载原生回调可能阻塞。

临时 renderer 在启动过程中可能退出。失败判断持有该进程句柄并在恢复后检查，不只按 PID 查询，以避免把被复用的 PID 当成仍存在的失败 renderer。

## 配置与发布

配置只保存时区和可选可执行路径，写入通过同目录临时文件替换完成。配置、构建结果和日志不提交到 Git。发布构建保留运行依赖的许可证文件。

本项目操作的是界面进程中的时区接口，不声称改变服务端时区或所有业务行为。没有修改应用文件，也没有持久化系统设置。

## 任务栏时钟

任务栏功能不向 Explorer 注入 Frida，也不拦截 Explorer 的时间 API。单独的线程使用 COM UI Automation 读取主屏 `Shell_TrayWnd` 中已知时钟元素的位置；支持 `SystemTray.DateTimeIcon` 和新版的 `SystemTray.OmniButton`。找不到已知元素时不按屏幕边缘猜测位置。

工具自己的 Win32 窗口使用 `WS_EX_LAYERED | WS_EX_TRANSPARENT | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`，在该矩形显示两行文字。点击穿透，窗口不抢焦点。位置每 500 毫秒检查一次，显示按分钟更新；时区切换在下一次检查生效。线程启用每屏 DPI 感知，让 UIA 坐标与绘制坐标一致。任务栏不可见或前台窗口覆盖时钟区域时隐藏显示层，重新可见后恢复。桌面窗口本身不算全屏应用。

时间使用 `GetSystemTime` 取得 UTC，再以明确的 `DYNAMIC_TIME_ZONE_INFORMATION` 调用 `SystemTimeToTzSpecificLocalTimeEx` 转换；从未调用修改系统时间或时区的接口。独立时钟停止时销毁窗口，Windows 原时钟始终在下面正常运行。会话内的命名互斥体防止多个工具实例同时覆盖时钟。

`taskbar.timeZone` 和 `taskbar.enabled` 与两应用的配置独立保存。启用状态使设置窗口关闭时继续运行，下次手动启动工具时自动恢复；不会注册系统开机启动。独立时钟仅显示主屏时间与月/日，系统日历面板、通知及副屏时钟不在覆盖范围。
